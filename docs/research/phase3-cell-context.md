# Phase 3 literature review: cell-line context features

## Summary
- DepMap's core omics/CRISPR files (expression, mutations, copy number, dependency, `Model.csv`) are downloadable per-release from the portal's Custom Downloads (filterable to specific ACH- IDs) and are stated by DepMap staff to be CC BY 4.0; the portal's live Terms & Conditions page could not be directly verified (bot-walled) so commercial/ML-training restriction claims found in search summaries should be treated as unconfirmed — pin a release and cite it, don't redistribute raw files.
- The field mostly encodes cell context as (a) basal/landmark expression (PaccMann: ~2,128 genes), (b) binary mutation vectors (DrugCell: top 15% mutated genes), or (c) a learned per-cell-line embedding/one-hot (CPA) — and learned embeddings are explicitly reported to be unable to represent genuinely new cell lines, which is the crux of question 4.
- Modern perturbation models (Arc Institute's State, used directly on Tahoe-100M) use the **mean control-cell profile as the cellular context input**, i.e. exactly this project's DMSO pseudobulk approach — but published benchmarks (Virtual Cell Challenge 2026) that rely on this always *give* the model the control profile of the held-out cell line at test time, unlike this project's `unseen_cell_line` spec.
- With only 8 training cell lines, no dimensionality-reduction or embedding should be *fit* on those 8 rows (classic factor-analysis guidance wants ≥5–10 observations per retained dimension); any PCA/embedding must be pre-fit on DepMap's full ~2,000-line panel and merely looked up/projected for the 8 (and any held-out) lines.
- Tahoe's own `cell_line_metadata` ships a small, CC0-licensed, curated driver-mutation table (`Driver_Gene_Symbol`, `Driver_VarZyg`, `Driver_VarType`, `Driver_ProtEffect_or_CdnaEffect`, `Driver_Mech_InferDM`, `Driver_GeneType_DM`) that needs no extra download or license review — useful as a cheap baseline feature set, but too sparse/low-rank across just 8 lines to be a full replacement for DepMap.

## 2. How published models encode cell context
- **PaccMann** (drug sensitivity, IC50): represents each cell line by a subset of ~2,128 genes selected via network propagation from expression data, with an attention mechanism over those genes [from abstract/secondary: arXiv 1811.06802 / NAR 2020 search synthesis — full text not fetched].
- **DrugCell**: binary mutation vector over the top 15% most-frequently-mutated cancer genes (~3,008 genes), fed into a Gene-Ontology-structured "visible" neural network [from abstract/secondary: GitHub/Cancer Cell 2020 search synthesis].
- **LINCS L1000 / cross-cell-line imputation work**: basal + drug-perturbed expression over 978 landmark genes, cast as a gene × drug × cell-type tensor; because most cells aren't screened against most drugs, models predict a given cell line's response from related drugs/cell types sharing the landmark space [from abstract/secondary].
- **CPA (Compositional Perturbation Autoencoder)**: encodes cell type/line as an annotated covariate with a learned embedding, disentangled from a perturbation embedding, enabling OOD recombination of already-seen covariates; however, search-synthesis of follow-on work states plainly that "learned categorical embeddings are tied to the cellular contexts observed during training and therefore cannot directly represent new cell lines or cell types encountered at application time," and that an alternative is to use the **mean control-cell profile** as the context input instead, which "can produce reasonably strong perturbation-response predictions across a range of control set sizes" [from abstract/secondary — biorxiv CPA full text was rate-limited (HTTP 429) on every fetch attempt, so this is WebSearch-tool synthesis, not a page I read directly].
- **Arc Institute "State" model** (used directly for perturbation prediction on Tahoe-100M): two-stage — a State Embedding (SE) model trained on ~167–270M observational cells to build a generalizable, noise-invariant cell representation, and a State Transition (ST) model that takes an unperturbed/control cell population plus a perturbation label and predicts the perturbed population, using set-transformer attention over covariate-matched chunks (best at chunks of 256 cells); the full ST model beats a pseudobulk/mean-pooling ablation and a single-cell variant [from abstract/secondary — biorxiv full text 429'd repeatedly]. On Tahoe-100M specifically, the reported pipeline computes **pseudobulk per (cell line, molecule), log-normalizes, and defines the perturbation delta as pseudobulk minus a control-mean profile (averaged control wells)** — i.e. essentially the same DMSO-pseudobulk-logFC design already used in this project [from abstract/secondary].
- **Tahoe-x1**: a billion-parameter foundation model trained on Tahoe-100M; its embeddings are reported to combine with the State ST model to improve context generalization over raw expression [from abstract/secondary].
- **Virtual Cell Challenge 2026**: frames "unseen cells generalization" as predicting response in cell lines never perturbed during training, but explicitly **gives models the unperturbed/control state of those held-out lines** plus the perturbation list as input — it does not test the harder case (this project's) where even the control is withheld [from abstract/secondary]. A companion benchmarking paper reports that a **simple linear baseline sometimes outperforms complex/foundation models including STATE** in this setting [from abstract/secondary].
- Drug-sensitivity ablation work (not perturbation-response, but informs feature-importance intuition): one search-summarized paper reports mutation status as the single most important cell-line feature type, ahead of expression [from abstract/secondary — specific paper not identified with full confidence, treat as a soft prior, not a strong citation].

## 3. Generalization to unseen cell lines, few lines, dimensionality
No paper directly addressing "8 training cell lines" was found; evidence is indirect. A 2026 bioRxiv preprint, "Widespread data leakage inflates performance estimates in cancer drug response prediction," reports that supervised feature screening done across the whole dataset before cross-validation (a widespread practice) inflates apparent accuracy — leakage-free CV raised mean squared error by 16.6% on average across 265 drugs and 1,462 cell lines, and an audit of 32 published methods (2017–2024) found leakage in 23 of them (72%) [from abstract/secondary — full text 429'd on every fetch attempt]. This is a strong, directly applicable warning for this project: with only 8 cell lines, any feature selection, scaling, or PCA fit that touches held-out folds (even indirectly, e.g. fitting on "all 8 lines" before a leave-one-line-out split) risks the same inflation, at even higher relative risk given the tiny n.

On multi-omics vs. single modality, search-summarized work on drug response prediction found that adding more omics modalities "raises concerns regarding model generalization" when a modality is missing at deployment, i.e. more features are not free — they can hurt portability, not just help [from abstract/secondary].

On dimensionality vs. sample size: classical guidance for PCA/factor analysis (not perturbation-modeling-specific) recommends roughly 5–10 observations per retained component/dimension to avoid components that are "too sample specific," with the commonly cited Nunnally (1978) 10:1 rule flagged in follow-up literature as not strongly empirically supported but still widely used as a conservative bound [from abstract/secondary — MRC-CBU stats FAQ, Wikipedia "one in ten rule"]. Applied here: fitting any reduction on the project's own n=8 cell lines is well below even the loosest version of this rule (would support fitting at most ~1 dimension, and even that is marginal) — the reduction must be **pre-fit externally** (on DepMap's ~2,000-line panel) and only the 8 (or held-out) lines' coordinates looked up.

## 4. The control-profile question
Using the in-experiment control (DMSO pseudobulk) as a cell-context feature is common in the current perturbation-modeling literature — it is, per the abstract-level description above, essentially what Arc Institute's State/ST model does for its Tahoe-100M evaluation (control-mean profile as context, perturbation delta as target) [from abstract/secondary]. It is *not* obviously leakage when both the control and the drug-response label come from the same held-in cell line (random / unseen_drug splits): the control is an input describing the cell line's basal state, not the outcome being predicted, so conditioning on it is standard covariate use, not label leakage.

It **is** unusable by construction for `unseen_cell_line` and `both_unseen` in this project's own spec, because the held-out line's DMSO control is not available at training/inference time — this matches how the field's more permissive benchmarks are actually run (Virtual Cell Challenge 2026 *does* supply the held-out line's control state, which is precisely why control-as-context models can work there) [from abstract/secondary]. Since this project's spec deliberately withholds it, any model architecture that needs the control profile cannot be evaluated on those two splits and this should be stated as a documented limitation rather than worked around (e.g., don't impute a fake control from a similar line and call it equivalent — that would reintroduce a leakage-like assumption).

DepMap basal expression is the natural substitute because it is measured independently of the Tahoe experiment and is available in principle for any characterized-but-unscreened line — matching the eval spec's allowance. The tradeoff to note (and test, see Ablation 2 below) is a platform/batch difference: DepMap's basal RNA-seq is generated under standard monoculture, while Tahoe's DMSO pseudobulk comes from the "cell village" co-culture Mosaic platform — the two are not guaranteed to agree closely even for the same 8 lines, and this project has the ability to check that empirically since both exist for the same 8 lines.

## 5. Tahoe's own `cell_line_metadata`
Confirmed by reading the Hugging Face `tahoebio/Tahoe-100M` README directly [verified: source read]: `cell_line_metadata` includes `cell_name`, `Cell_ID_DepMap`, `Cell_ID_Cellosaurus`, `Organ`, and driver-mutation columns `Driver_Gene_Symbol` (HGNC symbol of a known/putative driver gene with functional alteration), `Driver_VarZyg` (zygosity), `Driver_VarType` (e.g. Missense/Frameshift/Stopgain/Deletion), `Driver_ProtEffect_or_CdnaEffect`, `Driver_Mech_InferDM` (inferred LoF/GoF), and `Driver_GeneType_DM` (Oncogene/Suppressor classification). The dataset (including this table) is released under **CC0 1.0** (public domain) [verified: source read], and the full Tahoe-100M download is roughly 337 GB / ~1.69 TB uncompressed [verified: source read] — not relevant to the metadata table's own (tiny) size, but confirms the bulk data is not something to touch for this phase.

This table is a good lightweight, zero-license-risk, zero-extra-download feature source — effectively a curated subset of what `OmicsSomaticMutations` already contains, restricted to known cancer drivers. It is not a full substitute for DepMap: it captures only driver genes (a handful per line), so across just 8 cell lines several may share the same one or two canonical drivers (e.g. TP53), giving this feature set very low effective rank/variance at this project's scale. Best used as a cheap, interpretable ablation feature set alongside, not instead of, DepMap-derived basal expression.

## Recommendation for this project
- **Files + release pin**: `Model.csv` (ACH- ID join), `OmicsExpressionProteinCodingGenesTPMLogp1.csv` (continuous basal-expression feature), and a damaging/somatic mutation matrix (e.g. `OmicsSomaticMutationsMatrixDamaging.csv`) restricted to the 8 ACH- IDs via the portal's Custom Downloads filter — pin to whatever the current named quarterly release is at build time (25Q2 file list confirmed directly; a later release such as 26Q1 was announced and may be current by the time this is built) and record the exact release string + file names + a checksum in the download script. *Justification*: expression + mutation covers the two feature families every reviewed model (PaccMann, DrugCell, State) treats as primary, while CN/CRISPR dependency are lower-priority nice-to-haves given the 16GB/€0 constraint and the small marginal value multi-omics showed in the generalization literature above.
- **Encoding + dimension for 8 lines**: fit a PCA (or just take top-variance genes) on the *full* DepMap expression panel (~2,000 lines), then project only the 8 (and any held-out) lines into that space, keeping a small number of components (single digits, not tens) as ridge-model input; do not fit any reduction on the project's own 8 rows. *Justification*: the ≥5–10-observations-per-dimension guideline and the leakage-paper's warning both argue against learning anything statistical from n=8; a reduction fit externally sidesteps both.
- **Controls**: use DMSO pseudobulk as a feature/ablation only for `random` and `unseen_drug` splits (where it's legitimately available); for `unseen_cell_line`/`both_unseen`, use the DepMap-basal-expression projection instead and explicitly document that control-dependent model variants are not evaluable on those two splits. *Justification*: matches this project's own eval spec and avoids reproducing the leakage-adjacent shortcut that Virtual-Cell-Challenge-style benchmarks take (supplying the held-out control) but that this project intentionally does not allow.
- **Ablations**: (1) DepMap-PCA-projection + driver/mutation flags vs. a pure one-hot/mean-response baseline, run across all four splits — tests whether omics features earn their keep at all, expected to matter only on the two unseen-cell-line splits since one-hot literally cannot extrapolate there. (2) DMSO-pseudobulk-as-context vs. DepMap-basal-expression-as-context, run on the `random` split where both exist — quantifies the platform/batch gap between Tahoe's co-culture basal state and DepMap's monoculture RNA-seq, which directly bounds how much the forced DepMap fallback on held-out lines should be expected to cost. *Justification*: both are cheap (reuse the same downloaded files), directly test this project's two open design questions, and give a variance estimate before committing to a final feature spec.
- **What 8 lines can/cannot support**: 8 lines can support a fixed, externally-validated per-line feature lookup (pre-fit PCA, curated driver flags), a directional answer to "do omics features help over one-hot at all," and a qualitative case study of the control-vs-DepMap tradeoff. They **cannot** support fitting/tuning any new embedding or dimensionality reduction from scratch, and a leave-one-line-out sweep over only 8 folds is high-variance and underpowered for a confident, general claim about unseen-cell-line performance — results should be reported as an illustrative case study on this slice, with the explicit caveat that Tahoe's full 50-line set (and DepMap's ~2,000-line panel for feature pre-fitting) is what a statistically defensible generalization claim would require.
